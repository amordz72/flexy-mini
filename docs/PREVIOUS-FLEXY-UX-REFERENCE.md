## تصحيح الفهم واعتماد بوابة الفحص

- **USER-STATED**: المستخدم يريد إدخال رقم الزبون مرة واحدة في فليكسي، مع وضع رصيد عادي وخيار إرسال عادي أو الضغط على عروض لنفس الرقم. هذا يطابق أساس الواجهة القديمة، وليس طلب إنشاء صفحة رقم ثانية.
- **لا ننسخ تطبيق هني روحك** أو نحكم على Flexy Mini من صورته، ولا نستنتج أن عنصرًا غير موجود لأنه خارج منطقة لقطة الشاشة.
- قبل كل استنتاج UI: حدّد مصدر الصورة؛ راجع كود MyTool وTehna القديم وقرارات Developer؛ راجع كود Flexy Mini الحالي وBuild SHA الموجود على هاتف المستخدم؛ اكتب الفارق المثبت بين السابق والحالي والمرجع الخارجي.
- لا نخلط **فتح قائمة العروض أو استكشافها** مع **تأكيد وتنفيذ شحن**. عند تغيير الرقم لا تظهر نتائج الرقم السابق، ولا نبدأ USSD لمجرد فتح الصفحة.
- التباين بين إصدارات MyTool (Auto Discovery أحيانًا) وTehna Core (عند طلب عروض) يُعرض كتباين، ولا يُحسم بتخمين.
- **لا تغييرات كود أو قاعدة بيانات في هذه المهمة**. لا تغيير لمسارات الدفع أو الصلاحيات أو مخزون البطاقات استجابة للصور فقط.
- بعد أمر تنفيذ واضح، يقرأ المطور الملفات الفعلية ثم يغيّر موضعًا محددًا ويختبره، ويحدّث هذه الوثيقة بالأدلة؛ لا يبدأ الواجهة أو النظام من الصفر.

## متابعة التنفيذ 2026-10-13

بأمر المستخدم الحالي تم الرجوع للمصادر المذكورة أعلاه فعليًا ثم تعديل الفرق المحدد: رصيد افتراضي، رقم موحد، مسح حالة الرقم القديم، عروض تقرأ Cache ثم تأكيد استعلام عند الحاجة. لا Discovery تلقائي مع فتح الصفحة أو الإدخال، ولا نقل Backend Tehna. أصبحت متابعة نتيجة Station تلقائية للقراءة فقط. تفاصيل التنفيذ والاختبارات/حدود النشر في `SYSTEM-BEHAVIOR-MAP.md` §13. الادعاء السابق بأن البداية offers موجودة في المصدر أصبح تاريخيًا بعد هذا التعديل. الشحن العادي ومسارات Arsselli للعروض غير المعتمدة تبقى غير مفعلة.
